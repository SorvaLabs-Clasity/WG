GitHub Control Hub

Continuous checks on a GitHub organization and the AWS account behind it.

Build v1.0.78 6 Lambda functions 12 DynamoDB tables 0 servers

Scope

What it covers

GitHub organization

Read continuously

  • Repository access, by person and by team
  • Branch protection and rulesets
  • Dependabot alerts and coverage
  • Renovate pull requests
  • Stale and blocked pull requests
  • Detailed GitHub logging

AWS account

Read continuously, corrected on request

  • S3 bucket policies and public access
  • CloudWatch log group retention
  • Resource configuration against defined rules
  • Change events via CloudTrail

Feature

Security alerts

Raised from GitHub webhooks as changes happen, not found on a sweep. Each alert stays open until someone resolves it.

Critical

Immediate

  • Repository made public
  • Branch protection removed entirely
  • Repository ruleset deleted

High and medium

Reviewed

  • Protection drift, rules modified rather than removed
  • Team permissions changed on a repository
  • Admin added to a repository
  • Team added or removed from a repository
  • User promoted or team access elevated
Pipeline
GitHub → API Gateway → webhook-receiver Lambda → SQS queue → webhook-worker Lambda. The queue means a burst of events is absorbed rather than dropped, and a failure is retried instead of lost.
Why a queue
The receiver only validates the signature and enqueues, so GitHub gets an immediate answer. All the work happens in the worker, out of band.
Stored
One row per alert with its severity, repository, and time of the change. No expiry.
Resolution
Manual, or automatic when the same condition is observed to have been reversed.

Architecture

Where it runs

Where it runs

Desktop application

Electron Local backend localhost:4321 Self-updating release

Runs on the operator's machine and uses the operator's own AWS access - SSO, a named profile, or session keys. It holds no credential of its own. GitHub credentials are read from Secrets Manager in the connected AWS account at startup, so reach into GitHub is gated behind AWS access.

Nothing is stored on the machine beyond the selected profile name. The OAuth callback returns to localhost, so a sign-in code never passes through a shared server.

Sessions do not survive a restart. The session token is held in sessionStorage, which the browser clears when the window closes. Only the login name and avatar persist, in localStorage, enough to offer "Continue with name", holding no access of its own. The sign-in that follows is a real one; it is quick because GitHub recognises the browser.

The token is a JWT signed with a secret held in Secrets Manager rather than on the machine, so rotating it ends every outstanding session at once.

Feature

Access map

Answers
Who can reach a repository, and by which route: directly, through a team, or as an organization owner.
Runs in
graph-aggregator Lambda, on an EventBridge rule. Nothing else writes this table.
Source
Full walk of the GitHub API: every repository, its collaborators, its teams, its branches.
Stored
graph-edges, one row per connection, holding subject, repository and role.
Refresh
Three tiers. Webhooks patch individual rows as changes arrive; a light pass re-reads repository metadata and team composition every 30 minutes; the full walk rebuilds everything once a night, at 22:00 America/New_York.
Why three
The full walk is four requests per repository, about 1,300 for 300. The facts six checks depend on cost almost nothing: repository metadata arrives with the listing, team composition is two calls per team. Refreshing the cheap half often and the expensive half rarely is what keeps those checks current without spending the rate limit.
Cost
≈ 4 GitHub requests per repository. 300 repositories ≈ 1,300 requests, against 15,000 per hour.
Staleness
Last rebuild time is displayed on the page, not inferred.

Feature

Who knows this

Answers
Who to ask about a repository, a path inside one, or a library used anywhere in the organization. The question behind it is "this broke at 3am, who do I wake".
Runs in
The application, on demand. No schedule and nothing stored: a question asked during an incident deserves a live answer, and a cached one would be stale exactly when it matters. Three requests for a repository, one for a path, one search plus up to twelve history reads for a library.
Reads with
The asker's own GitHub token, never the application's. This concerns a repository they may not be allowed to see, so GitHub decides what they can read rather than the application reimplementing that rule.
Signals
Commits, who changed it, weight 1.0. Reviews, who read it, 0.7. Comments, who discussed it, 0.25. A review sits close to a commit deliberately: during an incident the person who reviewed the change that broke it is often the fastest to recognise it.
Ranking
Recency is applied per contribution rather than to the total, halving every 90 days, so ten commits last week outrank two hundred from three years ago. Scores are then normalised to 100 against the top person, because the question is who to ask first rather than how expert anyone is in the abstract.
Excluded
Bots, which would otherwise top every list and push the humans off it. Matched on "bot" as a whole word so Abbot and Robotics are not caught, and Copilot by name, which that test cannot catch.
A library
"Who knows React" is answered by finding the files that declare it — package.json, go.mod, requirements.txt — and reading the history of those files. Whoever added, bumped or removed the dependency is the answer. Searching commit messages for the name instead would return whoever typed the word, which is mostly release bots.
Not lockfiles
A lockfile names the library too, but is rewritten whenever anyone installs anything. Counted, it would make whoever last ran an install the expert on every dependency in the project.
Counts are a floor
GitHub returns one page, so a hundred results means "at least a hundred", not a hundred. The answer says when it is a sample rather than reporting the page size as a total.

Feature

AWS guardrails

Answers
Whether each resource of a covered type matches a defined rule.
Runs in
guardrail-enforcer Lambda, in the account being checked, under an IAM role listing named actions. Three of which are writes.
Triggers
Two EventBridge rules: a 15-minute schedule, and a CloudTrail event pattern matching six API calls. Both target the same function, with a dead-letter queue behind them so a failed invocation is retained rather than lost.
Stored
One finding per resource checked, whatever the verdict, replaced on each sweep. See the next slide.
Enforcement
Report by default. Enforce is enabled per rule. Every correction is logged with an undo.
Drift
Each evaluation is independent of the last. A reverted setting is a violation again and is corrected again.
Deployment
Can run in an account with no GitHub components deployed at all.

Feature

How a finding is produced

The AWS tab opens instantly because it is not asking AWS. Every figure on it was worked out beforehand and stored. This is that path, end to end.

1 · Trigger
A 15-minute EventBridge schedule, or a CloudTrail event pattern matching six API calls, which re-checks only the resource that changed. Both invoke the same Lambda; a dead-letter queue holds anything that fails five times, with a CloudWatch alarm on it.
2 · Collect
Per resource type rather than per rule. S3 lists buckets and, for each, its policy, encryption, public-access block and tags; CloudWatch Logs lists log groups and their retention and tags. Optional settings that are simply absent are recorded as absent rather than treated as errors, because a bucket with no policy is an ordinary bucket.
3 · Exclude
Before evaluation, not after. A resource matched by a rule's exclusion list is recorded as not applicable with the list and clause that matched, and is never evaluated or written to. This ordering is what stops the per-resource Fix button touching a resource somebody deliberately carved out.
4 · Evaluate
Each remaining resource against the rule's parameters, producing one of three verdicts: compliant, violation, or not applicable. A rule set to enforce then corrects a violation and records what it changed; a rule set to report writes the finding and stops. Report is the default.
5 · Store
One row per resource per rule in the aws-findings table, keyed account # region # rule # resource. Every verdict is stored, not only failures, so the tab can distinguish "checked and fine" from "never checked". A sweep overwrites the rows it produced.
6 · Read
Opening the tab is a single query against that table, sorted violations first. No AWS API call, no evaluation, no waiting. Refresh re-reads the stored rows; Sweep all runs steps 1 to 5 again.

Consequence worth stating: a finding can be up to an hour old, and the screen is showing the last sweep's conclusion rather than the account's current state. Where a change fired a CloudTrail event, which is the ordinary case, it is seconds old.

Feature

Why both a schedule and an event

CloudTrail is the fast path and the sweep is the floor. Five things can stop the fast path firing, and the sweep is unaffected by all of them.

No trail
The event rule reads CloudTrail. An account without a trail logging management events never fires it at all, and the guardrails would be silent rather than slow. The sweep needs nothing but the schedule.
An unmatched call
CloudTrail records every API call made in the account, of which S3 alone has around a hundred. The rule listens for six names, chosen because they are the ones that can change what the two current rules check. A future rule about, say, bucket encryption would care about PutBucketEncryption, which is not on the list, and would be found by the sweep rather than in seconds until the list grew.
A rule that opted out
Each rule has a Reacts to changes switch. Turned off, that rule is skipped by the event path entirely and the sweep is the only thing that ever runs it. The rule card says which: within seconds, or waits for the sweep.
A missed delivery
Four ways an event does not arrive, none of them exotic. CloudTrail delivers management events on a best-effort basis and typically within about fifteen minutes, not instantly. EventBridge retries a failing target for 24 hours and then gives up. A Lambda that throws five times sends the event to the dead-letter queue, where it waits for a person rather than being reprocessed. And the trail itself can be stopped, deleted or have its S3 bucket policy broken, at which point the events simply stop with nothing announcing it. In every case the schedule is what notices.
A new rule
Adding a rule does not retroactively fire events for resources that already exist. The first sweep after it is created is what checks the estate against it.
Cost of the floor
About 11 cents a month. It was four times that at a fifteen-minute interval, which bought a worst case of fifteen minutes instead of an hour on a path that is already the fallback. Under a quarter of one percent of the Lambda free allowance.

The two together give the same guarantee twice over: normally a drift is corrected in seconds, and if anything about the fast path fails the worst case is an hour rather than never.

Feature

Alarms and notification

Answers
Any check, above or below a threshold, routed to an email group.
Runs in
alarm-evaluator Lambda, on a 5-minute EventBridge schedule. It re-runs each armed alarm's check itself, so an alarm fires whether or not anyone has the application open.
Delivery path
Lambda → SNS topic → email. One topic per group, created when the group is created.
Stored
Threshold, recipients, and current firing state. State is what makes a notification a change rather than a repeat.
Delivery
SNS, one topic per group. Recipients confirm their own subscription.

Feature

Pull request reminders

Answers
Pull requests approved and unmerged, awaiting review, or stale beyond a configured interval.
Runs in
The same alarm-evaluator Lambda, on the same 5-minute schedule. One invocation does both jobs rather than two functions waking separately.
Source
Read from GitHub during that pass. One request returns a page of open pull requests together with their reviews and status, rather than one request per pull request.
Stored
A snapshot of the list, and per pull request: last reminder, its comment id, and any pause or mute.
Comments
One per pull request. Each reminder deletes the previous before posting.
Overrides
Mute per person, organization-wide or per repository. Pause per pull request.
Display
Snapshot served under 15 minutes old, refreshed in the background. Manual refresh forces a live read.

Interface

REST and GraphQL

Default
The REST API, for everything that reads one thing at a time: repository settings, branch protection, collaborators, team membership.
GraphQL
Used where one question spans many objects and REST would require a request per object. Three distinct queries across six call sites.
Query 1
Open pull requests with their reviews, requested reviewers, last commit and check status. One request covers a page. Serves the Pull requests tab, the reminder pass, and pull request alarms.
Query 2
Which repositories have Dependabot enabled, walked across the organization in one query rather than a page of names per repository.
Query 3
Pull request review counts, for two checks: stale branch protections, and ranking repositories by protection bypasses.
Rate limits
Separate budgets. REST is 15,000 requests an hour per installation; GraphQL is 5,000 points an hour, where a point cost is calculated from how many objects a query could return rather than from the number of calls.
Page size
Learned rather than configured. A GraphQL query's cost scales with the page requested, and what an organization can afford depends on its own pull request volume, so the application discovers the size once and stores it.

Feature

Activity log

Streams
Three: actions taken in the application, changes reported by GitHub, and AWS guardrail findings.
Retention
13 months, stamped on each row from that row's own timestamp. Nothing is deleted on an age-of-system basis.
Always recorded
Changes to structure and access: repositories created, deleted or made public; branch protection and rulesets changing.
Detailed logging
An administrator toggle that additionally records routine traffic: branches and tags, commits pushed, pull requests opened, merged and closed. Each kind can be disabled individually.
On turning it off
Collection stops; nothing already recorded is removed. Rows keep their full retention and remain visible, and a view filter hides them for readers who do not want them.
Runs in
The webhook worker Lambda. No additional infrastructure: it records deliveries the application already receives.
Reversal
Actions taken by the application record an undo where one exists.
