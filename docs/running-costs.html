Correction

An earlier version of this page omitted the WAF entirely, priced API Gateway as an HTTP API rather than the REST API actually deployed, and left out CloudWatch alarms and KMS. It also treated the account's free tier as available, which it usually is not, and counted CloudTrail, which almost every account already runs for its own reasons. The figures above replace those, and come from Cost Explorer rather than from a model.

The WAF is the bill

Six dollars a month, fixed, whatever the organization does. Everything else put together is under a dollar.

AWS WAF charges $5.00 per Web ACL per month and $1.00 per rule per month before a single request is inspected. The deployment has one of each. Request charges are $0.60 per million and, at 3,623 requests in 25 days, round to nothing.

It sits in front of the webhook API and holds exactly one rule: a rate limit of 2,000 requests per five minutes per source address. It deliberately does not use the AWS common rule set, because two of those rules would reject legitimate deliveries. The body size cap is 8 KB and GitHub payloads routinely exceed it, and the XSS and SQL-injection body rules inspect what on a webhook is somebody's branch name or commit message.

Is it worth six dollars

That is a judgement rather than a calculation, and it is worth making deliberately. The controls that actually gate the endpoint are the API Gateway resource policy, which admits only GitHub's published address ranges, and the HMAC signature the receiver verifies before anything is queued. The WAF is defence in depth on top of both.

Removing it would cut the fixed floor by 91% and leave two other controls in place. Keeping it costs about seventy dollars a year. Both are defensible; what is not defensible is paying for it without knowing it is there, which is what the previous version of this page allowed.

The one index worth its cost

repo-index duplicates the rows it covers, which is what an index does. It stays small because it is sparse: a row that is not about one repository omits the attribute entirely rather than storing an empty string, so roughly a third of rows are not indexed at all. Storing "" would have indexed every one of them under a single empty key.

Measured against the alternative it replaces: about one cent a month at 500 events a day, and 28 cents at 5,000. What it buys is that filtering the feed by a repository returns every match at any depth instead of giving up after three thousand rows.

Reads cost more than writes here, which is unusual and worth knowing: 738,728 read units against 95,230 write units. Most of that is the graph rebuild scanning the edge table to work out what changed before writing the difference. That scan is what keeps the write count low, so it is a deliberate trade and a good one, since reads are a fifth of the price of writes.

Why the light pass is nearly free

The full rebuild costs four requests per repository. The light pass costs zero per repository: everything it writes arrives inside the listing response it was already paying for. That is why it can run twelve times more often for a fraction of the traffic, and why six otherwise-stale checks are current within thirty minutes rather than six hours.

Rate limits

15,000 requests per hour, per installation, shared by everything.

The application authenticates as a GitHub App installation, which on Enterprise Cloud gets 15,000 REST requests per hour. Scheduled rebuilds, widget checks and page loads all draw on the same pool.

The secondary limit

Separate from the hourly quota, GitHub enforces a burst and concurrency limit that triggers regardless of the hourly figure. This is why the alarm pass runs its checks sequentially: firing every check in the same instant is exactly the shape that trips it.

The commit-search endpoint is stricter again, at 30 requests per minute. The three subject-by-subject checks that use it are budgeted at 25 accounts per pass and cache answers for 48 hours, which is why those widgets fill in progressively rather than answering at once.

GraphQL, exactly where

Six call sites, three distinct queries, metered against a separate budget of 5,000 points per hour rather than the 15,000 REST requests.

Query 1 · open pull requests

Defined once as OPEN_PRS_QUERY in services/prNudgeService.ts. A search over open pull requests returning, per node: number, head branch, author, repository, last commit date, statusCheckRollup, requested reviewers and latestReviews. Three call sites share it:

Call siteUse caseToken
routes/pulls.ts Drawing the Pull requests tab The caller's own. The App token can see every private repository, so using it would show somebody pull requests they cannot open on github.com
services/prNudgeService.ts The 5-minute pass that decides which pull requests have gone quiet and posts a reminder App installation
alarms/handler.ts Pull request state for alarm evaluation, so an alarm on stale pull requests can fire App installation

Query 2 · Dependabot status per repository

fetchRepoAlertStatus in services/dependencyService.ts, called from routes/dependencies.ts. Walks organization.repositories to find which repositories have Dependabot enabled at all. The comment in the code is explicit about why it is GraphQL: doing it over REST would be four more pages fetching names GraphQL has already handed over.

Query 3 · pull request reviews, for two widget checks

Two near-identical queries in services/graphService.ts, each asking repository.pullRequests.nodes.reviews.totalCount:

CheckUse case
stale-branch-protections Finds protection rules that no longer match how the repository is actually used, by looking at whether recent pull requests were reviewed at all
protection-bypasses-ranking Ranks repositories by how often protection was bypassed, which needs review counts per pull request
Why the pull request page size is learned rather than configured

A GraphQL query's point cost scales with the page requested, and the size an organization can afford is a property of that organization: how many pull requests, how many reviewers, how much CI. The app discovers it by asking for a large page and stepping down when GitHub gives up, then stores the answer in org-config. Held in memory alone, that discovery ran once per process, which meant twenty to thirty seconds on the first load of the tab after every app launch and again after every Lambda cold start.

What "1,035 repositories" means

The full rebuild runs inside a Lambda function, and 900 seconds is the hard maximum a Lambda may run for. It cannot be raised, by configuration or by paying more. On the live deployment the rebuild takes 310 seconds for 356 repositories, which is about 0.87 seconds per repository. Multiply that out and it reaches 900 seconds at roughly 1,035 repositories.

This is not a cost ceiling. It is the size at which the six-hourly rebuild stops finishing.

Why that is worse than it sounds

The rebuild writes its edges only at the end, so a run that times out writes nothing. The symptom would be a graph that silently stops updating while the light pass keeps working, which is close to the failure this deployment already had for a different reason.

The fix when it comes is to make the rebuild resumable, walking a slice per invocation and keeping a cursor, rather than doing it all in one pass. That is a real piece of work and it is not needed yet.
