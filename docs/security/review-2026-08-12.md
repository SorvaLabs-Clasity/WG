# Security review — 12 August 2026

A second full pass, after [the one earlier this month](review-2026-08.md).
That review covered dependencies, the page's remote origins, and the
infrastructure at rest. This one went through the request path: what each route
authenticates, what it authorises, and who can reach it.

Dependencies are unchanged and clean — `npm audit` reports nothing across the
workspace, backend, frontend, desktop and infra, except the `brace-expansion`
advisory that the postinstall patch already replaces on disk. See the note in
the previous review; the situation has not moved.

Everything below was found in application code and configuration.

## Fixed

| Finding | Severity | Fix |
|---|---|---|
| `GET /auth/system-token` returned the GitHub App installation token — admin over every repository — with no authentication | **Critical** | Route deleted; the one caller reads it in-process |
| The desktop backend listened on `0.0.0.0`, publishing that API to the local network | **Critical** | Binds `127.0.0.1` |
| Rule-template create/edit/delete had no authorization, alone among the org-wide config routes | **High** | Gated on the admin team |
| The AWS setup endpoints accepted cross-site POSTs (CSRF) | Medium | `Origin` / `Sec-Fetch-Site` check |
| One-time auth codes were read then deleted, and expiry was left to DynamoDB TTL | Medium | Atomic `Delete … ALL_OLD`, expiry checked in code |
| The TLS private key was `chmod 644` on the instance | Medium | `600`, owned by the uid the container runs as |
| `jwt.verify` named no algorithm | Low | Pinned to `HS256` on both sides |
| `contents: write` granted to every job in the release workflow | Low | Read by default; write only on the release job |

## The two that mattered

### An org-admin token, available to anyone who asked

```ts
router.get("/system-token", serverModeGuard, (_req, res) => {
  res.json({ token: getSystemToken() });
});
```

`serverModeGuard` blocks this on EC2. It does nothing on the desktop app, which
is where the route existed to be used. There was no other check: no session, no
origin, nothing. Anything that could open a socket to the app could ask for the
GitHub App installation token and receive it — admin across every repository in
the organisation.

Its only caller was the auto-updater, which needs the token to fetch releases
from a private repo. That code runs in the Electron main process, and the
backend is `require()`d into that same process by `desktop/src/server.ts`. The
token was being sent out over TCP and read back in by the process that already
had it in memory.

It now calls `getSystemToken()` directly. A function call inside one process
cannot be reached from outside it, which is a stronger statement than any guard
on an HTTP route.

### Bound to every interface

```ts
server = expressApp.listen(port, () => { … });   // 0.0.0.0
```

`listen(port)` with no host binds all interfaces. On a laptop that means the
administrative API for a GitHub organisation and several AWS accounts was
reachable by anything on the same network — an office LAN, a conference wifi, a
café.

Together with the finding above, a stranger on the same network could have run:

```
curl http://<laptop>:4321/auth/system-token
```

and been handed org-wide GitHub admin. Neither finding needed the other to be
serious, but the combination is what makes this review's date worth recording.

The desktop listener and the dev server now bind `127.0.0.1`. The EC2 build is
deliberately unchanged: reaching it from outside is the entire point there, and
a security group decides who may.

## Rule templates, the one router nobody gated

Templates, exclusions, scanners, widgets, alerts and the config bundle all
refuse writes from outside the admin team. `config.ts` gates *importing* a rule
template. The rule-template routes themselves had no check at all, so any
member of the organisation could rewrite one.

A rule template is the protection preset the Protect modals offer and the
Templates page builds on. Editing one changes what an admin later applies to a
repository — under the admin's name and with the admin's token.

`repro-undo` greps the route files to assert every write route names a guard,
and it passed throughout, because it checks the files it is given and
`ruleTemplates.ts` was not one of them. It now also asserts that every route
file containing a write is either guarded or on an explicit list of routers
that are deliberately not org-wide, each with its reason. A new router can no
longer be invisible to it.

## Not fixed — update signatures

`desktop/src/main.ts` disables the updater's signature check:

```ts
(autoUpdater as any).verifyUpdateCodeSignature = () => Promise.resolve(null);
```

This is left alone on purpose. The app is built unsigned — `mac.identity` is
`null` and CI sets `CSC_IDENTITY_AUTO_DISCOVERY: false` — so restoring the check
would break Windows updates for every installed copy without making anything
safer. The override is a consequence of not signing, not an independent mistake.

What remains between an installed copy and a hostile update is HTTPS to the
GitHub API and the SHA-512 recorded in `latest.yml`. That covers a network
attacker; it does not cover anyone who can publish to the repository's releases.

The fix is to sign the builds, then delete that line:

1. Add a code-signing certificate to CI (`CSC_LINK`, `CSC_KEY_PASSWORD`) and,
   for macOS, notarisation credentials.
2. Remove `CSC_IDENTITY_AUTO_DISCOVERY: false` and `mac.identity: null`.
3. Remove the `verifyUpdateCodeSignature` override.

Until then it is worth knowing that write access to this repository's releases
is equivalent to code execution on every machine running the app.

## Checked, no action

- No SQL, command, or template injection; the one `spawn` remains shell-less
  with an allow-listed argument
- No path traversal — the AWS config parser reads fixed paths under `$HOME`
- No XSS sinks; `dangerouslySetInnerHTML` still appears nowhere, and the CSP
  forbids inline and remote script
- Webhook HMAC still fails closed, compares in constant time against raw bytes,
  and rejects replays
- Org membership is re-checked on every request, with a bounded stale window
- Repository writes still run with the caller's own GitHub token, so GitHub
  remains the authority for anything per-repo
- No credential in the working tree or in recent history
- IAM unchanged and still free of `iam:`, wildcard `AssumeRole`, and
  administrator roles — `repro-leastprivilege` covers this

## Deploying these

The application changes need a rebuild and redeploy; nothing here replaces the
EC2 instance, unlike the previous review.

```bash
cd github-control-hub/backend && npx tsc
cd ../frontend && npm run build
cd ../.. && ./scripts/deploy.sh <instance-id>
```

The private-key permission fix applies on the next `deploy.sh` run for an
existing instance, and from user-data on any new one.

Desktop users get the loopback binding and the removed token route with the
next released version.

## Verification

Reviewed independently, not from the change summary. Three mutations confirm
the new assertions are not vacuous: reinstating `GET /auth/system-token`,
removing a rule-template guard, and rebinding to every interface each make a
test fail.

The packaged app was run rather than reasoned about. It serves on loopback,
`localhost` still resolves to it, the LAN address refuses the connection,
`/auth/system-token` returns 404, and the updater reads its token in-process:

```
[updater] AWS authenticated, reading system token...
[updater] Token: got token
```

## Signing, and what it would buy

The updater's signature check is disabled because the builds are unsigned;
removing the override without signing would break Windows updates and improve
nothing.

What signing actually buys: **write access to this repository's releases is
currently equivalent to code execution on every machine running the app.** The
updater downloads and installs whatever the latest release contains, and has no
way to tell a genuine build from a substituted one.

That risk scales with how many people run it. For one or two people who control
the repository anyway, it is close to theoretical. For an organisation where
several admins install it and repository access is broader than the people who
build it, it is the largest remaining exposure in this project.

If the organisation already has code-signing certificates — most do — this is
configuration rather than expenditure:

| Platform | What is needed |
|---|---|
| macOS | Apple Developer Program membership; set `identity`, notarise |
| Windows | Any OV/EV code-signing certificate, or Azure Trusted Signing |

Then delete the `verifyUpdateCodeSignature` override in `desktop/src/main.ts`.
Signing without deleting it leaves the check off; deleting it without signing
breaks updates. They go together.
