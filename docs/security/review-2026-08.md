# Security review — August 2026

A full pass over dependencies, application code, and infrastructure.

## Fixed

| Finding | Severity | Fix |
|---|---|---|
| `index.html` loaded an unpinned `<script>` from unpkg, no integrity hash, into a session holding GitHub org admin | **High** | Icons and fonts vendored; nothing remote remains |
| Two further CDNs (cdnjs, Google Fonts) with no integrity checks | Medium | Same |
| Content-security policy disabled | Medium | Strict policy; `script-src 'self'`, no inline, no eval |
| `brace-expansion` DoS inside `aws-cdk-lib`'s bundled dependencies, unreachable by `overrides` | High advisory, low reachability | Postinstall replaces it — 35,358ms to 14ms on the advisory's own case |
| EC2 root volume unencrypted | Medium | `encrypted: true` |
| Dead-letter queue unencrypted, plaintext transport allowed | Low | SQS-managed encryption, `enforceSSL` |
| `spawn(…, shell: true)` with a user-supplied profile name | Low — allow-listed | `shell: false`, explicit `aws.cmd` on Windows |
| IMDSv2 not pinned in the infrastructure code | Low — already set on the instance | `requireImdsv2: true` |

### On the unpkg script

It is worth stating plainly, because it is the only finding here that was
genuinely dangerous. The tag was:

```html
<script src="https://unpkg.com/@phosphor-icons/web"></script>
```

No version, so whatever that package resolved to that day. No integrity hash,
so no way to notice a change. Loaded into a window already holding a signed-in
administrative session for a GitHub organisation and several AWS accounts. A
compromise at unpkg, a hijacked DNS answer, or a malicious publish to that
package would have executed with full access to the app's session.

Bundling costs a few hundred kilobytes in an application that is already
hundreds of megabytes.

### On brace-expansion

`aws-cdk-lib` ships its dependencies inside its own tarball, so npm installs
them from there rather than resolving them. `overrides` is ignored and
`npm audit fix` has nothing to fix. A postinstall replaces the file with the
patched version npm installs at the top level.

Reachability was always low — CDK uses it via minimatch for ignore patterns and
stack selectors, on inputs that are our own file paths. It is patched anyway,
because "not reachable today" has to be re-argued every time the surrounding
code changes.

Dependabot reads the lockfile, and the lockfile records what the tarball
contains, so the alert persists until AWS republishes. The code on disk is not
what it describes.

## Checked, no action

- No command injection, path traversal, SSRF, or dynamic evaluation of input
- No XSS sinks — `dangerouslySetInnerHTML` appears nowhere
- No credential committed, and none in recent history
- Every GitHub call scoped to the configured organisation; no route accepts a
  client-supplied owner
- Electron: context isolation on, node integration off, a narrow preload
- Rate limiting on authentication and on the API
- Docker image runs as a non-root user and carries no secrets
- Deploy bucket blocks public access and encrypts at rest
- `npm audit` clean across backend, frontend, desktop and infra

## Applying the infrastructure changes

EBS encryption and the IMDSv2 pin **replace the EC2 instance**. The Elastic IP
re-associates, so the webhook URL is unchanged, but the instance is new and
needs the application image deployed to it again:

```bash
cd github-control-hub/infra && npx cdk deploy -c enforce=true
./scripts/deploy.sh <new-instance-id>
```

Webhook deliveries during the replacement are lost, so avoid repository admin
while it runs.
