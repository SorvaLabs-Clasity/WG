GitHub Control Hub

01

The problem

2 min

Everything this app does, you can already do. You can open GitHub and check who has admin on a repository. You can open the AWS console and check whether a bucket is public. The problem was never that the information is hidden, it's that nobody looks on a Tuesday when nothing is wrong.

So this watches the things we said we cared about, and tells us when one of them stops being true. Two systems, one place: the GitHub organization, and the AWS account it runs on.

It's a desktop app. When you're clicking around in it, it runs on your machine using your AWS credentials. The scheduled half. The checks that run while nobody has it open, lives in AWS with its own tightly scoped permissions. Those are two different things, and I'll show you both.

Set the frame If you only land one idea, land this: the value isn't the dashboard, it's that something is checking when nobody is watching.
02

Signing in

1 min

Two connections, in this order. AWS first, because that's where the GitHub credentials live, then GitHub itself.

Nothing sensitive ships inside the app. Everything it needs to talk to GitHub, the organization name, and the private key for our GitHub App. Is stored in Secrets Manager, which is AWS's own encrypted store, inside your account.

So the order matters. You sign into AWS first; the app then uses that access to read the secret and pick up the GitHub credentials. If you can't reach AWS, you get nothing. Which is the correct failure. There is no copy of that key on anybody's laptop, and revoking someone's AWS access revokes their reach into GitHub too.

If you've used it before it offers "Continue with your-name". That is not a session left lying around. The token is gone the moment you close the app. All it remembers is who you were, which is enough to put your name on a button and nothing else. The sign-in still happens; it just doesn't ask you anything, because GitHub recognises the browser.

Show

  • The two-card sign-in screen, AWS, then GitHub.
  • Continue with… if it's offering it, one click, no password.
  • Use a different account, which is what clears GitHub's cookies.
  • The SSO tab: Create an SSO profile. The app writes ~/.aws/config for you, so nobody has to hand-edit it.
  • The account switcher in the top-right, if you have more than one account wired up.
Expect this question "So what runs the checks when the app is closed?". The scheduled work runs as AWS Lambda functions, each with its own IAM role. Not your credentials, and not a copy of them. Beat 06 has the exact list of what that role may do.

Under the hood

Your AWS access
Whatever profile you already use, SSO, a named profile, or pasted keys. The desktop app has no AWS credential of its own; it borrows yours for as long as it's open.
What's in the secret
One Secrets Manager entry holding the org name, the GitHub App's ID and installation ID, its private key, and the OAuth client id and secret. Read once at startup, and again whenever you switch account.
How GitHub access works
When you create a GitHub App, GitHub gives you a private key file. The app uses that key to sign a short "this really is me" request, and GitHub hands back a token that works for one hour. The app quietly fetches a new one about five minutes before the old expires, so it never runs on a dead token.
Why an App
Because the App belongs to the organization rather than to a person. A personal token leaves when its owner does, and carries everything that person can reach.
Signing in
GitHub redirects back to localhost:4321. The desktop app runs its own small backend, so your sign-in code never passes through a shared server.
"Continue with…"
Two things are remembered in two places. The session token sits in sessionStorage, which the browser clears when the window closes, so a restart really is signed out. Your login name and avatar sit in localStorage, which survives. That is all the button is: a memory of who you were, holding no access at all.
Why it feels instant
GitHub's own cookies live in Electron's session, so it recognises the browser and returns without a password prompt. The link carries ?login=<name> deliberately, without it GitHub signs in as whichever account its cookie holds, and "Continue with alice" can hand back bob.
Switching accounts
"Use a different account" deletes every github.com cookie from the Electron session, so the next sign-in asks properly.
The token
A JWT signed with a secret held in Secrets Manager, not on the machine, so rotating that secret signs everybody out at once.
Creating a profile
The same flow a TV app uses when it shows you a code to type on your phone: the app asks AWS for a code, opens your browser, you approve it there, and the app waits until AWS says you did. It then asks AWS which accounts and roles you actually have, so you pick from a list instead of typing a twelve-digit account number.
03

Overview, the dashboard you build yourself

3 min

This is the part people use daily. Each card is a question you asked once, and it keeps answering. "Which repositories have no owning team." "Which admins haven't committed in six months." "Which repos have a critical vulnerability."

Click into any card and you get the rows behind the number, searchable, sortable, and you can drag the column widths, because a repository name is longer than a status.

Show

  • The grid of widgets. Point at one that has a real finding.
  • Click into it, the detail table. Drag a column edge to widen the name.
  • Add a widget: pick a check, name it, save. It appears for everyone.

Under the hood

Storage
A widget is just a saved row in DynamoDB. A check id and a title. It holds no data of its own.
Where answers come from
Most checks never call GitHub at all. They read a copy we keep in DynamoDB. A table of "who can reach what", one row per connection, like alice → api-repo, role: admin. "Repos without an owning team" is counting rows in that table, which is why it's instant. Beat 04 is where that table comes from.
The expensive ones
A few questions can't be answered from that table. "has this admin committed recently" needs a live search per person, and GitHub allows only 30 searches a minute. So each person's answer is stored with the date it was checked, and each pass refreshes the 25 least recently checked. Over a few passes everyone gets covered.
What's stored
One row per person per check, holding the verdict and when it was taken, kept 48 hours. "Checked and clean" is stored too. Otherwise a clean account would be indistinguishable from one nobody has got to yet, and coverage could never complete.
Partial answers
If it can't check everyone, it refuses and says so rather than showing a smaller number. "Twenty of forty-five admins are dormant" isn't a smaller finding, it's an unreliable one.
One dashboard
Shared by everyone, not per-user. That's why only admins can edit it.
04

Access map. Who can reach what

2 min

The question this answers is the one you get asked in an incident, or by an auditor, and it's genuinely hard to answer from GitHub's own UI: who has access to this repository, and how, directly, through a team, or because they're an org owner.

You can come at it from either end. Pick a person and see everything they can reach. Pick a repository and see everyone who can reach it.

Show

  • Search a person → their repositories, and the route to each.
  • Switch to Repos → pick one → the people and teams on it.
  • Or Teams → pick one → its members and its repositories, both clickable.
  • Point at the freshness note in the header. It says how old the picture is.

Under the hood

What it actually is
A DynamoDB table called graph-edges. One row per connection: a person or team on one side, a repository on the other, and the role between them. A few thousand rows for a few hundred repositories. Nothing clever. The value is that it's already here when you ask.
How we get it
A Lambda walks GitHub's API every 6 hours, every repository, its collaborators, its teams, its branches, clears the table and writes the result. Roughly four requests per repository: about 1,300 for 300 repos, against an allowance of 15,000 an hour.
Why not just webhooks
Webhooks are the fast path, not the whole story. GitHub only sends one for certain events, they can be missed if we're down when it fires, and they can arrive out of order. So they patch the rows they cover (a member added, a team changed, branch protection edited) and the 6-hourly rebuild is the safety net that re-establishes the truth regardless.
And a light pass, every 30 minutes
The backstop. Same Lambda, different payload, { mode: "light" } rather than "full".

Why the light one is cheap
None of what it reads is per-repository. Repository metadata arrives with the listing at no extra cost, and team composition is two calls per team. The expensive part of the full walk, collaborators, branches, workflows and alerts, four requests each, is exactly what it skips.
Why that was added
Six checks read facts nothing but the full rebuild wrote, so re-running them every five minutes gave the same answer seventy-one times out of seventy-two. The app was told when a repository went public, it raises a critical alert on that exact event, and then left the widget counting public repositories stale for hours. Those events now patch the graph too.
What that means for you
Anything GitHub sends an event for shows up in seconds. Anything else is at most half an hour old. The freshness note is on screen either way, rather than hidden.
One detail
The rebuild timestamp lives in a different table, because the rebuild wipes this one first. A marker stored inside would be destroyed by a run that then crashed, leaving no record it ever tried.
05

Vulnerabilities

2 min

Two halves of one question. Dependabot says what's vulnerable; Renovate says what's been raised to fix it. They're separate tabs because they're separate questions - and a third tab for who gets emailed about either.

The number worth pointing at isn't the alert count. It's coverage, how many repositories are actually being scanned. A repository with Dependabot switched off reports zero vulnerabilities, and zero looks like good news.

Show

  • The headline strip, critical, high, and "not watching". Dwell on that last one.
  • Switch to the Renovate tab, one click, not a scroll.
  • The Notifications tab. Who gets told, for both.

Under the hood

Alerts
Read org-wide in a single call, not per repository, the difference between one request and several hundred.
Ambiguity
"No alerts" and "scanning switched off" are stored as different things, so a clean repository never looks like a vanished one.
Renovate, specifically
Nothing about Renovate is stored. There's no Renovate API to ask, so the app runs a live GitHub search. Literally is:pr org:<org> author:<bot>, every time you open the tab, and holds the answer for two minutes so switching tabs doesn't re-ask. That's why the bot's account name is a setting: authorship is the only marker a Renovate pull request carries.
Dependabot, by contrast
Also read live, but org-wide, and the results feed the widgets too, so opening this tab and having a vulnerability widget on the dashboard costs one fetch, not two.
Partial reads
If only part of the org can be read, the sweep reports degraded rather than returning what it managed. An alarm treats that as no reading, so it can't resolve itself on half an answer.
06

AWS guardrails

3 min

This is the half that isn't about GitHub at all. A guardrail is a rule about how a kind of AWS resource must be configured. Buckets aren't public, log groups have a retention set. And it gets checked on a schedule, and again within seconds of anything relevant changing.

The second part is the interesting one. CloudTrail. AWS's own record of who did what , tells us the moment somebody creates a bucket or changes a retention policy, and the check runs on that one resource straight away. You don't find out at the next sweep. You find out now.

And if a rule is set to enforce, that's also when it gets put back. Someone drops a log retention from a year to a week; changing retention is one of the six calls we watch; the rule sees it and sets it back within seconds. The re-check afterwards finds it compliant and writes nothing, so it settles rather than looping.

Show

  • The rules list, with pass/fail counts per rule.
  • Open a failing rule → the specific resources, with the reason.
  • Show an exclusion, the deliberate "we know, and it's fine" case.

Under the hood

Sweep
Every 15 minutes, one Lambda, across every rule.
On change
An EventBridge rule watches CloudTrail for six specific API calls and invokes the same function within seconds, scoped to the one resource.
Findings
Written in batches. DynamoDB may decline part of a batch, so unwritten items are retried. An ignored decline is a violation reported nowhere.
Report vs enforce
Rules report by default. Enforcing is opt-in per rule, set in the AWS tab, because a rule that fixes things is a rule that can break things. Every fix it makes is written to the activity log with an undo.
Its own permissions
This is the part that runs with nobody logged in, so it has an IAM role of its own, and it's a named list, not a wildcard. It may read bucket policies and log settings; it may write exactly three things: a bucket policy, and setting or clearing a log retention. It cannot assume any other role, and it cannot read any stored credential.
Drift
Every sweep re-evaluates from scratch, it never trusts the last verdict. So a setting changed back is simply a violation again, and an enforcing rule fixes it again.
Standalone
This half can run in an account with no GitHub anything, no App key, no access graph, no webhook. That's how it's deployed to production.
07

Alarms and email

2 min

A dashboard nobody opens is a dashboard that doesn't work. So any widget can become an alarm: tell it a threshold, tell it who to email, and it watches on its own.

The rule it follows is worth saying out loud, an alarm fires on a change of state, not on every check. You get told when something breaks and when it's fixed, not every five minutes in between.

Show

  • Open a widget → Add alarm → threshold and recipients.
  • The Alarms tab, what's armed, what's currently firing.
  • An email group, so recipients are a list you maintain once.

Under the hood

What's stored
An alarm is a row in DynamoDB, which widget, what threshold, which email group, and whether it is currently firing. That last field is the whole trick: comparing it to the new reading is how the app knows this is a change rather than the same bad news again.
Evaluation
Every 5 minutes, one Lambda, reading the same stored answers the dashboard reads. So an alarm and the screen can never disagree.
Delivery
SNS, one topic per email group. Recipients confirm their own subscription. Nobody can silently add you to a list.
No reading ≠ good news
If a check can't complete, the alarm's state is left alone rather than resolved. A failure to look must never read as an all-clear.
Buffer
Pending notifications are held briefly and expire after 24 hours, so a backlog can't flood a mailbox days later.
08

Pull request reminders

2 min

The most human feature in here. It finds pull requests that have gone quiet, approved and unmerged, waiting on a review, stale for a week, and posts one comment naming the people who can actually unblock it.

One comment, not a pile. Each reminder replaces the last one, so a pull request that's been nudged four times has one comment on it, not four. And anyone can be muted, or a single pull request paused, when the reminder is wrong.

The tab opens instantly because it isn't asking GitHub while you wait. The same five-minute pass that decides who to remind also writes down what it saw, and the tab reads that. If it's older than fifteen minutes you get a live read instead, and there's a refresh button when you want to force one.

Show

  • The PR list, with why each one is flagged.
  • The settings: what counts as stale, and who gets named.
  • Pause one, or mute a person. Show the escape hatch.

Under the hood

Walk
Runs on the same 5-minute tick as alarms, using GraphQL so one request covers a page of pull requests with their reviews.
Why GraphQL here
Most of the app uses the REST API, which reads one thing at a time. This question spans many objects at once: every open pull request, plus its reviews, requested reviewers, last commit and check status. Over REST that is several requests per pull request. One GraphQL query returns a whole page of them. Three queries use it in total: this one (shared by the tab, the reminder pass and pull request alarms), a Dependabot-enabled walk across the organization, and review counts for two security checks. GraphQL is also metered separately, against 5,000 points an hour rather than the 15,000 REST requests, so it does not compete with the graph rebuild for the same budget.
What's stored
Two things. A snapshot, the whole list as the last pass saw it, one row, kept 24 hours, and a row per pull request holding when it was last reminded, the id of that comment, and any pause or mute. The pull requests themselves are not mirrored into DynamoDB; the snapshot is a cached answer, not a copy of GitHub.
How fresh
Rewritten every 5 minutes by the scheduled pass. The tab serves it if it's under 15 minutes old, refreshes behind you while you read, and goes live if it's older or if you press refresh.
Sticky comment
The previous reminder's id is stored, so the next one deletes it before posting.
Pauses persist
A paused pull request's state is explicitly kept alive. Otherwise it would expire and reminders would quietly resume on something you'd silenced.
09

The activity log

2 min

Everything the app does is recorded, and so is everything the organization does that matters. Three streams: actions taken in here, changes GitHub told us about, and AWS guardrail findings.

By default the organization stream holds what changed structure or access: a repository created, deleted, or made public, protection or a ruleset changing. Turn on detailed logging and it also records the routine traffic, branches, tags, pushes, pull requests, and you can pick which of those you want.

Worth saying out loud: turning it back off keeps everything already collected. It stops recording from that point. Nothing is deleted, and readers who find it noisy can hide those rows without changing what is collected.

Show

  • The three stream tabs.
  • The detailed logging toggle, and the kinds underneath it.
  • Expand a row to see what actually changed.
  • The Undo on an action the app took.

Under the hood

Retention
13 months, stamped per row from that row's own timestamp, a year of history plus a month of slack, so an auditor looking back twelve months finds a complete record.
Detailed logging
A toggle on the organization tab, admins only. It records webhook deliveries the app already receives, so there is no extra infrastructure and nothing new to configure in GitHub.
Turning it off
Prospective only. Collection stops; rows already written keep their full retention and stay visible, and the unchecked kinds are remembered for next time.
Lookups
Two extra indexes, so finding one row by id is a lookup rather than "check the newest rows and hope".
10

Closing

1 min

One thing I'd like you to take away, and it isn't a feature. Every screen in here distinguishes three states, not two: loading, there's nothing, and we couldn't find out.

Those last two look identical unless you make them different. And the empty one is reassuring. "Nothing outstanding." "No alarms." A tool that says that when it actually failed to look is worse than no tool, because now you believe it.

So a failed read says it failed, and says why. That's the standard the whole thing is built to, and it's the reason I'd trust it on a Tuesday when nobody's watching.

Land it here Don't end on a feature list. End on this. It's the thing that separates it from a dashboard somebody threw together, and it's the thing a security audience cares about.

Where the code runs

Desktop app
Electron, with its own backend on localhost. Everything you click happens here, with your credentials.
AWS account
Lambdas, DynamoDB, SNS, S3, Secrets Manager, all deployed from one CDK stack.
Two sets of credentials
Anything you click uses your AWS access, for as long as the app is open. Anything scheduled uses a Lambda role, a named list of actions, no ability to assume another role, and no access to stored credentials. There is no third thing: no hosted server, and no standing key that can reach the whole organization.

If they ask

The questions that actually come up, with an answer you can give in one breath.

What does it cost to run?

Everything is on-demand. No servers, no idle capacity. The cost drivers are Lambda invocations on those five schedules, DynamoDB on-demand reads and writes, and CloudWatch log storage.

Quote your actual figure from Cost Explorer rather than an estimate. If you haven't checked, say "it's on-demand across six small Lambdas and a dozen tables, and I'll send you the exact number". That's a better answer than a guess.

What permissions does it need on GitHub?

A GitHub App with read access to repositories, members, teams and Dependabot alerts, plus write on the few things it can change. It's an App, not a personal token, so it belongs to the organization, not to me, and it survives me leaving.

On the AWS side it's two separate things: the desktop app borrows whatever access you already have, and the scheduled Lambdas have their own roles listing exact actions. For the guardrail one, three write actions in total.

Can it change things, or only look?

Mostly look. It can post pull request reminders, toggle Dependabot on a repository, and remediate a guardrail. But remediation is opt-in per rule and off by default.

Everything it changes is written to the activity log, and most of it can be undone from there.

What happens if it breaks?

Nothing in your GitHub org or AWS account depends on it. It reads, it reports, and it emails. If it stops, you lose the watching, not the systems.

And it's built so a broken read looks broken rather than looking clean. That's the failure mode that matters.

Why a desktop app and not a website?

Because a website needs a server, and that server needs credentials that can reach everything, a single key to the whole organization, sitting somewhere, all the time.

This way each person uses their own AWS access. The only standing credentials are the Lambda roles, and those can't do much: read some configuration, write three specific settings, and touch this app's own tables.

Does it work for more than one AWS account?

Yes, you switch accounts from inside the app. And an account can run the AWS guardrails half with nothing GitHub-related deployed to it at all, which is how production is set up.

How is it deployed and updated?

The AWS side is one CDK stack. The desktop app builds in CI on merge and publishes a release; the app updates itself and shows its version on the sign-in screen.

Who can change the dashboard?

There's one dashboard shared by the whole team, so editing is limited to an admin group. Otherwise anyone could delete a card everyone relies on.
