# Design Context

## Target audience
The people who administer one company's GitHub organization and the AWS account
behind it: a handful of engineers and one or two admins, using this daily and
under time pressure. They are technically fluent. They are not looking at this
for pleasure — they open it because something needs deciding, and they want the
answer before they want the interface.

## Use cases
1. Read the organization's posture at a glance and find which checks need work.
2. Find the one pull request, repository, person or finding that is in the way.
3. Act on it — change a protection, add an alarm, close a gap — and see what
   the change actually did.
4. Read the record of what changed, who changed it, and when.
5. Set up who gets told about what.

## Brand personality / tone

The app is **written once and set five ways**. Every screen is composed from one
vocabulary, and a *theme* decides what each part of that vocabulary looks like.
No page knows which theme is running.

**Broadsheet** (the default) is a printed sheet: warm paper, warm ink, hairline
rules, a display serif for everything the page is *about*, and a humanist sans
for everything that helps you read it.

**Control** is the design the app wore before: rounded cards on a cool
blue-grey ground, real shadows, Inter set heavy and tight, saturated status
colour. Kept because it is a perfectly good way to read a dashboard.

**Terminal** is an engineering console: one monospace doing every job, a ground
ruled into a faint 24px grid, hard 1px boxes, bracketed controls, and a single
phosphor green. Light is a drafting sheet; dark is a CRT.

**Swiss** is the international style: a neue-grotesque set large and flat, a
visible column grid, a great deal of white, one signal red, and rules drawn in
the ink itself. Size and position do the ranking a border would otherwise do.

**Risograph** is brutalist print: two flat inks overprinted on newsprint, 2px
black rules, and shadows that are hard offsets rather than blurs. Buttons press
into their own shadow.

Every theme has two **editions**, light and dark, and they are the same theme
either way — no glow, no second accent palette, no separate dark design
pretending to be the same one. The two axes are independent: choosing a theme
never changes your edition, and switching edition never changes your theme.

Colour means one thing in all five. Four inks carry state — danger, caution,
settled, notable — and nothing else on any page is saturated. What changes
between themes is *which* four and how loud, never what they signify.

## The vocabulary
The part every theme reinterprets. Adding a screen means composing from these,
not inventing a sixth idiom that only one theme knows how to draw.

- **Masthead** — two tiers: the title of the paper over a heavy rule, and the
  section line under it. The current section is inked and underlined.
- **Headline and standfirst** — every screen opens with a serif headline and an
  italic serif line under it, closed off by a heavy rule.
- **Ledger strip** — a screen's standing: a rule in the state's ink, then
  figures in the display serif divided by column rules. One per screen.
- **Record** — one item in a list of them: a ruled box with a marginal bar in
  the state's ink down its left edge. It washes on hover; it never lifts.
- **Dateline** — facts separated by middots, newspaper style.
- **Small capitals** — the only label idiom. Section heads, column heads,
  eyebrows, legends and most controls are letterspaced small caps.
- **Text link** — the default action affordance, because a printed page has no
  raised rectangles on it.
- **Stamp** — the one filled control: a square inked block with reversed-out
  small capitals, reserved for the single action a screen is for.
- **Ruled field** — an input is an underline, never a box.
- **Figures** — every number the app reports is set in the display serif,
  tabular, with its column head in small caps beneath it.

## How a theme is built
Three things are variables rather than literals, and that is the whole trick:

- **colour** — every Tailwind colour resolves to `rgb(var(--x))`
- **shape** — every radius and shadow step resolves to `var(--r-*)` / `var(--shadow-*)`
- **type** — the display, running and monospace faces are `var(--font-*)`

The idiom classes in `src/index.css` are written against those same variables,
so a theme is a block of variables plus, where it differs in kind rather than
in degree, a short list of class overrides. Two attributes carry the choice —
`data-skin` and `data-edition` — and neither is required to be on the root,
which is why the theme picker's previews are running copies rather than
pictures.

Theme overrides are written `:where([data-skin="x"]) .caps`, never
`[data-skin="x"] .caps`. The `:where()` holds them at the same specificity as
the base class, so a theme beats the idiom while an inline Tailwind utility
still beats the theme. Without it, `className="caps text-ink"` silently stops
working.

Three themes are additionally allowed to reach a handful of *utilities*
(`border`, `border-rule`, `border-t-2`) because their identity depends on the
weight or colour of lines the markup writes literally. That list is in
`index.css`, it is short, and it should stay short.

## Constraints
- React 19 + TypeScript + Tailwind, and an Electron shell around the same build.
- **No remote origins.** This app holds an administrative session over a GitHub
  organization and several AWS accounts, so it must never fetch a font, a
  script or a stylesheet from an origin it does not control. The display serif
  is therefore a system stack (Iowan Old Style → Charter → Palatino → Georgia),
  not a webfont.
- Colour lives in CSS variables that flip between the two editions, and every
  Tailwind colour resolves through them. A token almost never needs a `dark:`
  half; where one appears, it is because the two editions want different
  *treatment*, not different values of the same treatment.
- Radius is zero app-wide and every shadow resolves to none. Depth is a rule.
- Data density matters more than breathing room: these screens routinely carry
  a thousand repositories, and a layout that is comfortable at six rows and
  unusable at six hundred is the wrong layout.
- Honesty is a design requirement. A failed read is said plainly and never
  rendered as an empty result; a stored answer says how old it is; a count that
  a filter is deciding says so beside the count.
